## Architecture & Conventions
- `lib/routes/app_routes.dart` defines 9 routes; `app_pages.dart` has `home`/`chat`/`notifications` commented out — `MainView` (`lib/view/Profile/main_view.dart`) reflects this: `PageView` children are `[Container(), FriendsView(), FindPeopleView(), ProfileView()]` with tab 0 labeled "Chats" but rendering an empty `Container`. Don't uncomment routes without restoring `HomeView`/`ChatView`.
- Services: `lib/services/auth_service.dart` (93 LOC) and `lib/services/firestore_service.dart` (~740 LOC, single god-service for all 6 collections). Controllers instantiate `FirestoreService()` directly — no singleton, no repository abstraction. Collections are literal strings: `users`, `friend_requests`, `friendships`, `chats`, `messages`, `notifications`.
- DI order matters: `SplashView` (`lib/view/auth/splash_view.dart:42`) does `Get.put(AuthController(), permanent: true)` *after* a 3s delay; every other controller does `Get.find<AuthController>()` in field initializers. Creating a controller before splash completes will throw. Prefer moving `AuthController` init to `main()` if you touch auth flow.
- Controllers import deep Get internals (`get_core/src/get_main.dart`, `get_rx/src/...`) — fragile on `get` upgrades; prefer `package:get/get.dart`.
- Models in `lib/models/`: `user_model`, `chat_model`, `message_model`, `friendship_model`, `friend_request_model`, `notification_model` — all manual copyWith.

## Firebase / Data Gotchas
- **Timestamp mismatch:** `UserModel.toMap` writes `Timestamp.fromDate`, others write `millisecondsSinceEpoch` ints (`ChatModel`, `MessageModel`, etc.). `UserModel.fromMap` handles both; `ChatModel.fromMap` does not — don't mix types without fixing deserializers.
- **Messages are top-level** (`collection('messages')` with `senderId`/`receiverId`), not subcollection under `chats`. `getMessagesStream` (`firestore_service.dart:563`) uses `where('senderId', whereIn: [A,B])` then client-filters + extra `chats/doc` read — expensive. `getFriendsStream:321` does `where(user1Id==)` stream + per-event `get()` for `user2Id` (second half not streamed, N+1).
- **Full-collection streams:** `getAllUsersStream` is bound in 3 controllers (`HomeController`, `UsersListController`, `FriendRequestsController`) — every client downloads all users, no `limit`/pagination, no server-side `!= currentUser` filter.
- **No composite indexes file** — queries like `friend_requests where receiverId== && status== orderBy createdAt` will require manual index creation in Firebase console on first run.
- **`blockUser` will throw** if no `friendships` doc exists (`update` on missing doc) — needs `set(merge:true)`.
- **IDs:** notifications use `DateTime.now().millisecondsSinceEpoch.toString()` (collision risk); friend requests use `Uuid.v4()` (`lib/controllers/users_list_controller.dart:173`).

## Common Pitfalls (would miss without reading code)
- `AuthService.signInWithEmailAndPassword` returns `null` unconditionally (`lib/services/auth_service.dart:26`) — `AuthController` relies on `authStateChanges` stream for navigation, not the return value.
- `FirestoreService.sendMessage(chatId, message)` shadows its `chatId` param (`lib/services/firestore_service.dart:539` re-declares `String chatId = await createOrGetChat(...)`).
- `HomeController.getOtherUser` contains a nested dead `fromLastMessageTime` function due to missing brace (`lib/controllers/home_controller.dart:90-115`) — search/sort can misbehave.
- `ProfileController` binds a stream + `ever` in `_loadUserData` but never cancels; `displayNameController` not disposed (`lib/controllers/profile_controller.dart:32-36`). `HomeController.onClose` is empty while holding `bindStream` bindings — leaks.
- `ProfileController.updateProfile` sets `_isLoading=true` but never resets it (finally only resets `_isEditing`).
- `HomeController.refreshChats` is a `Future.delayed(1s)` no-op — not a real refresh.
- `MainController.getUnreadCount/getNotificationCount` `try/catch Get.find<HomeController>` — returns 0 silently if `HomeController` was never `lazyPut` (which it isn't when Home tab is stubbed).

## AI Development Rules

- Never make broad refactors unless explicitly requested.
- Before modifying multiple files, explain the plan and identify affected files.
- Preserve the existing GetX + Firebase architecture unless a change is explicitly requested.
- Prefer small, incremental changes over rewriting working code.
- After code changes, run `flutter analyze` and relevant tests.
- Never delete existing functionality to make a new feature work.
- For UI work, prioritize responsive layouts, consistent spacing, typography hierarchy, accessibility, loading states, empty states, and error states.
- For Firebase work, consider security rules, read/write costs, realtime behavior, pagination, and data consistency before implementation.
- When unsure about an existing behavior, inspect the relevant code before changing it.
- Keep explanations in French, but keep code, filenames, commands, APIs, and technical identifiers in English.
